Context & problem

Corex is a web platform for health professionals and currently serves coaches. It includes a 4-step wizard for ISAK anthropometric assessments (body composition, Heath-Carter somatotype, Phantom Z-scores, charts and comparison between assessments), Monday-to-Sunday training routines built from an exercise catalog, and nutrition plans with BMR, TDEE and daily macros. Four roles (admin, coach, analyst and user) share the platform; one person can hold several and switch between them.

It started as a Google Apps Script prototype and was migrated to Next.js 14 + Supabase. It handles personal and health data, so access control lives in PostgreSQL (RLS), not only in the UI. It is in production and in use.

My role & constraints

  • Independent project, built solo for friends’ businesses: product, code, database, deployment and operations (CI and backups).
  • AI-assisted development with Claude Code under a written protocol that applies to every change, whatever its size: audit → diagnose → plan → ask for approval → implement only what was approved. If a plan fails midway, it is reverted and a new plan is written.
  • Every plan is rehearsed in full in a throwaway clone and measured (gate, lint, typecheck, tests and build) against main; if any number gets worse, the change is cancelled.
  • Operating constraints: free-tier plans (Supabase Free has no backups, hence a dedicated workflow), secrets are never printed (only their presence or length is checked), and real user data is never used as an example.

Architecture & decisions

  1. Active role in a JWT claim users cannot edit

    The active role travels in the JWT's app metadata, which only a service-role Edge Function writes; the RLS helpers cross-check it against the person's active roles, so tampering with the claim can only reduce permissions, never escalate them. The trade-off: every role switch requires a session refresh so the new JWT reaches Postgres.

  2. RLS switched on for every new table

    An event trigger on ddl_command_end enables RLS on any new table in the public schema, as defense in depth if a migration forgets to. The trade-off is that a new table starts closed until it gets policies; the edit-lock table is deliberately left that way and is reached only through SECURITY DEFINER functions.

  3. R15: every server action checked for an auth guard

    Gate rule R15 walks every 'use server' file and statically requires each exported function to call a guard that resolves the person from the session (not from an argument) before any read or write. The cost is enforcing a code shape the check can parse and listing every exception with its reason (login happens before a session exists); an unused exception also fails the gate.

  4. R19: every write returns rows

    R19 requires every Supabase UPDATE or DELETE in the app to request the row back: a write that RLS filters raises no error, touches 0 rows, and the app would report success. It means returning rows on every write; the exception list exists and is empty today.

  5. AI report: consent and anonymization enforced server-side

    The report Edge Function checks the consent stored on the row itself before sending anything to Gemini, and sends only anthropometry, with no name, email or ID number; coach notes are sanitized and wrapped in per-request random markers, and any output that copies them is rejected. The 5-agent pipeline takes 1–2 minutes, so it runs in the background, and if any agent fails no partial report is saved.

Results

  • Core modules working: a 4-step ISAK wizard with body composition, Heath-Carter somatotype, Phantom Z-scores and comparison between assessments; Monday-to-Sunday routines built from an exercise catalog; nutrition plans with BMR, TDEE and daily macros.
  • Access enforced in PostgreSQL: 25 tables with RLS and 72 policies, all scoped to authenticated users. Role switching is real at the RLS level (an admin acting as a user sees only their own data), and a user receives their ISAK report only after the coach publishes it: the policy filters it, not the UI.
  • A single gate runs on every commit and in CI: the 19 repo rules, deno check and deno lint for the Edge Functions, ESLint, tsc and the tests. CI adds the build, and a pre-push hook blocks pushes to main while the latest CI run on main is red.
  • Daily database backup, encrypted with AES-256-GCM with the key wrapped by RSA-OAEP, kept for 30 days. Every Sunday it is restored into a local Supabase and row counts for the key tables are compared; the result is recorded in the database even if a step fails.
  • Per-response nonce CSP with strict-dynamic, no 'unsafe-inline' in script-src, and writes rejected when the Origin does not match the Host.
  • 11-dimension 360 audit with a scorecard: the 2026-06-01 baseline came out at 4 green, 4 yellow and 3 red; after remediation on 2026-06-02, all 11 were green.

Lessons & next steps

  • Whatever can be checked in code becomes a gate rule: each rule has a number and states what it protects, its exceptions live inside the rule with their reason, and an exception that is no longer used also fails the commit.
  • Explicit source of truth: live DB > code > docs. The versioned schema is regenerated by introspecting the live database and, before opening to users, the migration history was consolidated into a clean four-file baseline.
  • With AI in the loop, the approved plan works as a contract: exactly what was approved gets executed, and a change that removes a feature, a guarantee or a test without an equivalent replacement is not carried out.
  • Documented next steps: offline support (service worker + IndexedDB), native Capacitor features (camera, push, filesystem), end-to-end tests for full flows, and advanced routines (RIR, tempo, rep ranges) with start and end dates for routines and plans.
