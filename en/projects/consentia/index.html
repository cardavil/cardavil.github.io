Consentia

Informed consent and e-signatures for small businesses.

Context & problem

In Colombia, a medical practice, a beauty clinic, a tattoo studio, a foundation or a school needs informed consent forms and data-processing authorizations that hold up legally. The product thesis is that there is no standalone consent product: the real alternative is buying a full industry software suite or staying on paper. Buyers want something simple that meets their compliance obligations without changing their software or their cloud.

Consentia keeps two modes separate per request, because mixing them blurs the legal nature of each: consent (a PDF with “I have read and accept” clauses that are never pre-checked) and document (a visual editor to place signature, date, initials, checkbox and text fields on a PDF, with up to 7 signers). It is not a document management system: the sealed PDF and the history log stay in the customer's cloud. It is a simple electronic signature under Colombian law (Law 527 of 1999, Decree 2364 of 2012), so its value lies in the evidence: IP taken from the edge, per-channel timestamps, a SHA-256 hash per signer and a global hash printed on every page.

My role & constraints

  • Independent project, built solo for friends’ businesses (hence its pilot clients): product definition, architecture, database, backend, frontend, deployment and operations.
  • AI-assisted development with Claude Code under a protocol written into the repository: audit, diagnose, plan, get explicit approval, then implement only what was approved. If a plan turns out to be incomplete midway, the work is reverted and re-planned. The protocol is backed by 13 skills and 5 versioned rule files.
  • Design constraints set in writing: never store signers' personal data in the permanent database, never mix consent and signature in the same request, and never operate external services through a CLI; everything goes through MCP or repo scripts with tokens in environment variables, so work never lands on the wrong project.
  • Constrained infrastructure: a static frontend with no framework and no build step, a Supabase backend, frontend releases only by pushing to main, and a design ceiling of 300 customer accounts.

Architecture & decisions

  1. Per-function JWT policy, declared in a single file

    Of the 13 Edge Functions, 8 turn off the gateway's JWT check because they are called by actors without a session (the signer, the auth hook, cron jobs, public verification and a webhook) and authenticate in code instead: a 256-bit per-signer token plus OTP, a webhook signature or a header secret. Each function's setting lives in config.toml; the deploy script reads it, aborts if it is missing, requires the project identifier to match across two repo files, and checks the value actually applied. The trade-off is that those 8 functions rely entirely on code, not on the gateway, for authentication.

  2. Documents stay in the customer's own cloud, with the narrowest permission

    PDFs and the history log (one CSV per year) live in the customer's Drive or OneDrive; the platform does not keep the document. On Google the app moved to the drive.file permission, which only allows access to files the app itself created, so every PDF is uploaded through the UI instead of being picked from an existing folder. That removed the only restricted permission and the annual security assessment (CASA) it required. In exchange, the CSV log is read-modify-write rather than an atomic append, so each write is serialized with a per-customer lock held in the database.

  3. External watchdog with a read-only secret

    The monitor that sends every alert is triggered by pg_cron, so if pg_cron dies nothing is left to report it. A GitHub Actions workflow, outside Supabase, checks a heartbeat using its own secret that only allows reads: reusing the monitor's secret would have allowed forcing a real run and moving the alert cursor past events not yet reported. The same heartbeat checks that the platform's email sender is still alive. Trade-off: GitHub's scheduled runs are delayed or dropped under load, so the job runs three times an hour and the alert thresholds were set from the measured gap.

  4. Signer data is purged at sealing

    Signers' personal data lives only in a temporary table and is deleted when the document is sealed; the database keeps hashes, record numbers and timestamps. The one exception is bounded: if delivery to the customer's Drive or the copies fail, that data survives only until the request expires (120 hours at most) so delivery can be retried at no charge, and is then purged. The trade-off is that the evidence must be self-contained: the exact inputs to each hash are attached as JSON inside the sealed PDF itself.

  5. Neutral delivery channels to preserve non-repudiation

    If the invitation and the code were sent from the customer's own accounts, the customer, who benefits from the signature, could read both and sign on the signer's behalf. So the link is sent from the platform's email account and the one-time code through an SMS aggregator on a platform account; only the copy of the already-signed document goes out from the customer's account. The trade-off is that the platform processes the signer's email and phone transiently: data minimization applies to content, not to delivery.

Results

  • Three-phase MVP implemented and deployed at consentia.com.co: consent, a visual signature editor with reusable templates and up to 7 signers, and two-channel signer verification (email + SMS).
  • Verifiable multi-tenant isolation: all 24 tables in the production schema have RLS enabled (26 policies), and a 45-case SQL harness simulates the anonymous and authenticated roles inside a transaction that is rolled back.
  • The same quality gate runs on pre-commit and in CI: lint, type-check, 343 Deno tests, a custom 39-rule linter and a page check. CI also regenerates the schema from production with a read-only token and fails if the versioned mirror (functions, tables, RLS, grants and cron jobs) has drifted; the pre-push hook repeats that check.
  • Public QR verification without exposing data: the browser computes the PDF's SHA-256 locally and compares it with the record without uploading the file, then extracts the attached JSON files and recomputes each signer hash and the global hash.
  • Automated operations and reporting: 7 pg_cron jobs (request expiry every 15 minutes, code purging, idle-session revocation every 5 minutes, an hourly monitor, a daily evidence archive with no personal data, and expiry of credit lots and orders), alerts by email and Telegram, and an indicators dashboard showing the state of each job.
  • 37 architecture decisions recorded with their origin, rejected alternatives and consequences; superseded ones are kept and marked rather than rewritten.

Lessons & next steps

  • A deployment path that has never been run is not validated: the one first chosen (sending the files inline through an MCP call) could not fit the largest function, which only surfaced on the first real deploy. It was replaced by a script that reads from disk and turns the written warning into a check that aborts.
  • Measure the infrastructure before setting thresholds: the external watchdog assumed hourly detection, but GitHub's scheduled runs are delayed or dropped under load. The thresholds were set from the measured gap, not the nominal schedule.
  • A check counts only once it has been seen to fail: each new linter rule is tested by seeding the defect in a throwaway clone before it is accepted, and a number is either measured or left out.
  • Next steps stated in the docs: a live end-to-end validation with the field checklist, a staging environment before running with paying customers, and third-party timestamping (RFC 3161 or OpenTimestamps).
