How I work

I build with AI coding assistants inside a control environment I designed. Layered instructions, guardrails that check every action, independent reviewers and automated gates decide what the AI can do. Nothing reaches production without passing them and my approval.

It’s the logic of banking operations (maker-checker, change control, an audit trail) applied to software. The pieces below are real, taken from my projects; each project uses the ones its risk calls for.

The life of a change

  1. Session start

    Before any work, the session receives the git state, the latest CI runs and the guardrails’ self-test.

  2. Audit

    Every claim is backed by a line of code (file:line), a database query or a measurement. A second pass looks only for assumptions, and what can’t be checked is listed as “not verified”.

  3. Plan with fixed sections

    • Today vs proposed.
    • Why it’s the smallest solution.
    • Impact on what already exists, ending with a mandatory “does not degrade” line.
    • Current code next to proposed code.
    • Verified vs not verified.

  4. Independent review

    A reviewer agent checks the plan against my decisions and the code. Each finding is fixed or answered before the plan reaches me.

  5. My approval

    An explicit OK for that change. If the plan proves wrong halfway, the work is reverted and planned again, never patched on the fly.

  6. Rehearsal

    The change is built in a disposable copy, and tests, types and the build are measured before and after. A new test counts only after it has been seen failing.

  7. Commit

    Every file and line of the diff is matched against the approved plan, counterparts are reviewed, and files are added by name.

  8. Gates and merge

    Local checks, then a pull request merged only when CI is green on its latest commit.

  9. Release

    By script, with live verification afterwards.

  10. Resume

    If the conversation is compacted, the state is rebuilt from disk (git, the written plan, the live source), never from the conversation’s summary.

Guardrails before every action

Before each action, the guardrails read the command, the file or the tool call, and decide.

When the AI tries to…DecisionWhy
print a secret, dump the environment or read a .env or key filedeniedonce a value is in the AI’s context, nothing can take it out
delete a root or home folder, or discard uncommitted work (git reset --hard)denied, except inside a throwaway copythere is no way back
skip git checks (--no-verify, changing the hooks path, any force push)denieda check only counts if it can’t be skipped
log in interactively or put credentials in a URLdeniedaccess goes only through each project’s scoped token
run a production command, write SQL, migrate, deploy or mergeasks meproduction needs a yes to that specific action
run SQL inside a transaction that ends in rollbackalloweda rehearsal changes nothing
edit the guardrails’ own configurationasks methe AI can’t loosen its own controls
read, test or buildsilentallowing means saying nothing, so nothing is pre-approved
  • Design: one dispatcher runs every rule; “deny” beats “ask”; a rule that fails asks, it never allows.
  • No network inside the check: a check that times out would let the action through, so it never waits on the network.
  • Hard to fool: it reads commands the way the shell does. It catches quoted flags (git push "--force") and variable prefixes (VAR=1 git push -f). It also catches commands nested in another shell (bash -c "…", cmd /c rd /s /q C:\) and scripts passed through a heredoc.
  • Tested: 52 automated tests, and each rule was written after seeing its tests fail. A new version installs only after GitHub confirms its tag is on the main branch and its CI passed.

A real change, end to end

One project’s chat bot records bank movements, and it read amounts typed with decimal cents as 100 times larger. In Colombia a period separates thousands and a comma marks decimals.

  1. Found by searching, not by luck

    While fixing the same error on another screen, a search for every place that reads an amount turned up the bot.

  2. Audit

    The one function that reads the amount, every path that leads to it, and where the value is stored. A read-only database query confirmed no stored movement had been affected.

  3. Plan

    840.000 · 1'500.000 · 1500000correctunchanged

  4. Negative control

    Three new test scenarios. Two of them failed on the old code with exactly the wrong amounts, and the third proved that normal amounts don’t change.

  5. Release and verification

    CI green on the pull request; the deployed function was checked live and its logs had no errors.

  6. Declared, not hidden

    Not verified: a live conversation with the bot. The test bench covers the same function.

Mistakes become controls

  1. The AI makes a mistake

  2. It’s recorded

    What happened, the root cause, the rule that would have prevented it, and what it cost.

  3. It becomes a lesson

    One line that cites its origin and loads at the start of every session.

  4. If it happens again

    The lesson becomes an automated check (a guardrail or a gate) and leaves the written rules.

Example lessons

  • A claim about the code needs the line, read in full, not a name or a fragment.
  • Answering a question is not approving a change.
  • A recommendation about an external tool comes from reading all of it, not its README.
  • A new test only counts once it has been seen failing for the expected reason.

Documents that can’t drift

  • Generated, not written: the infrastructure diagrams on each project page and the database schema snapshot are generated from the code and the live database.
  • Checked: the gate fails if a document is missing from the index or a link to a document is broken. It also fails if an environment variable in code is undocumented, or a user manual quotes text that doesn’t exist in the app.
  • Protected: a guardrail stops the AI from editing a generated file by hand, and names the command that writes it.
