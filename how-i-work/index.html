How I work

I build with AI coding assistants inside a control environment I designed. Layered instructions, permission rules, hooks that check every action, independent reviewers and automated gates decide what the AI can do. Nothing reaches production without passing them and my approval.

In practice that means context engineering for the agent, hooks and scripts that enforce the rules instead of trusting them to be followed, and a change process with evidence at every step. Everything below is real and comes from my projects; each project uses what its risk calls for.

The setup, layer by layer

From the machine the AI runs on down to production. Each layer is a real tool, named as it’s called.

  1. Workstation

    settings · fine-grained tokens

    The AI’s file tools can’t read outside the project folders. Access goes through fine-grained tokens, each one limited to a single project or organization, kept in environment variables and never in the code.

    Guarantees: a session can’t wander into other files, and no credential lives in a repository.

  2. Permissions

    allow · ask · deny

    Claude Code’s own permission rules, set per project. Some actions are denied outright, such as staging everything at once (git add .) or a force push. Others always ask me first: SQL on the live database, migrations, function deploys and writes to GitHub through MCP (the protocol that connects the AI to outside services).

    Guarantees: the riskiest actions are refused or wait for my click, whatever the AI decides.

  3. Hooks

    plugin · PreToolUse · SessionStart

    Hooks are scripts that Claude Code runs at fixed moments. A plugin I maintain runs one before every action. Its six rules (secrets, destructive commands, git, production, tokens only and its own configuration) read the command, the file or the tool call, and deny it, ask me or stay silent. Another runs at session start and tests the rules.

    Guarantees: the same guardrails in every project, and the AI can’t loosen them without my yes.

  4. Prompt scaffolding

    CLAUDE.md · rules · lessons

    The instruction files the agent reads before it works. One CLAUDE.md per project: what it is, the protocol, rules that can’t be broken and which source wins. Path-scoped rules load only when the AI touches that folder, and the lessons file loads every session.

    Guarantees: the AI works from the project’s real rules, not from general habits.

  5. Skills

    SKILL.md

    Step-by-step procedures the agent follows: audit, plan, rehearse, review counterparts, commit, handle an incident, resume after a long session. The ones that touch production (deploy, migrate, handle secrets) only start when I call them (disable-model-invocation).

    Guarantees: the same steps every time, whoever starts the session.

  6. Subagents

    Read · Grep · Glob

    Separate agents limited to read-only tools: one checks the plan against my decisions and the code; another tries to refute each security finding.

    Guarantees: the AI’s output is challenged before I see it.

  7. Git hooks and CI

    pre-commit · pre-push · GitHub Actions

    The same checks run before every commit, before every push and in continuous integration (CI: the checks GitHub runs on every change). A push is blocked while the main branch’s CI is red, and the checks can’t be skipped.

    Guarantees: nothing broken gets in, and nothing gets in on top of something broken.

  8. Production scripts

    Node · Deno

    Deploy scripts confirm the target account and project before writing, can run dry (show what they would do without doing it) and check that what’s served is what was built. Database changes are rehearsed in a transaction that ends in rollback.

    A secret reaches a script only through its environment, and to check that a token exists, a script reports its name and length, never its value.

    Guarantees: production changes are deliberate, rehearsed and verified, and no secret gets printed.

The life of a change

  1. Session start
  2. Audit
  3. Plan
  4. Review
  5. Approval human checkpoint
  6. Rehearsal
  7. Commit
  8. Git hooks and CI automatic gate
  9. Release
  10. Resume

  1. Session start

    Before any work, a SessionStart hook hands the session the git state, the latest CI runs and the plugin’s self-test.

  2. Audit

    Every claim is backed by a line of code (file:line), a database query or a measurement. A second pass looks only for assumptions, and what can’t be checked is listed as “not verified”.

  3. Plan with fixed sections

    • Today vs proposed.
    • Why it’s the smallest solution.
    • Impact on what already exists, ending with a mandatory “does not degrade” line.
    • Current code next to proposed code.
    • Verified vs not verified.

  4. Independent review

    A reviewer subagent checks the plan against my decisions and the code. Each finding is fixed or answered before the plan reaches me.

  5. My approval

    An explicit OK for that change. If the plan proves wrong halfway, the work is reverted and planned again, never patched on the fly.

  6. Rehearsal

    The change is built in a disposable copy, and tests, types and the build are measured before and after. Test-first: a new test counts only after it has been seen failing (red before green).

  7. Commit

    Every file and line of the diff is matched against the approved plan, counterparts are reviewed, and files are added by name.

  8. Git hooks, CI and merge

    The pre-commit and pre-push hooks, then a pull request merged only when CI is green on its latest commit.

  9. Release

    By script, with live verification afterwards.

  10. Resume

    If the conversation is compacted, the state is rebuilt from disk (git, the written plan, the live source), never from the conversation’s summary.

Counterparts: if X exists, Y must exist

The code is reviewed as pairs, in both directions where it makes sense: a test whose function no longer exists is also a gap. A pair that fails manual review twice becomes an automated check.

Hooks before every action

Before each action, the plugin’s PreToolUse hook reads the command, the file or the tool call, and decides.

    • Design: one dispatcher runs every rule; “deny” beats “ask”; a rule that fails asks, it never allows.
    • No network inside the check: a hook that times out would let the action through, so it never waits on the network.
    • Hard to fool: it reads commands the way the shell does. It catches quoted flags (git push "--force") and variable prefixes (VAR=1 git push -f). It also catches commands nested in another shell (bash -c "…", cmd /c rd /s /q C:\) and scripts passed through a heredoc.
    • Tested: 52 automated tests, and each rule was written after seeing its tests fail. A new version installs only after GitHub confirms its tag is on the main branch and its CI passed.

    A real change, end to end

    One project’s chat bot records bank movements, and it read amounts typed with decimal cents as 100 times larger. In Colombia a period separates thousands and a comma marks decimals.

    1. Found by searching, not by luck

      While fixing the same error on another screen, a search for every place that reads an amount turned up the bot.

    2. Audit

      The one function that reads the amount, every path that leads to it, and where the value is stored. A read-only database query confirmed no stored movement had been affected.

    3. Plan

      TypedStored beforeStored after
      840.000 · 1'500.000 · 1500000correctunchanged
      840000,0084,000,000840,000
      840.000,5084,000,050asks for the amount without cents

    4. Negative control

      Three new test scenarios. Two of them failed on the old code with exactly the wrong amounts, and the third proved that normal amounts don’t change.

    5. Release and verification

      CI green on the pull request; the deployed function was checked live and its logs had no errors.

    6. Declared, not hidden

      Not verified: a live conversation with the bot. The test bench covers the same function.

    Mistakes become controls

    A post-incident loop: every mistake the AI makes ends up as a written lesson, and one that repeats ends up as a hook or a CI check.

    1. The AI makes a mistake

    2. It’s recorded

      In the project’s error log: what happened, the root cause, the rule that would have prevented it, and what it cost.

    3. It becomes a lesson

      One line that cites its origin and loads at the start of every session.

    4. If it happens again

      The lesson becomes an automated check (a hook or a CI check) and leaves the written rules.

    Example lessons

    • A claim about the code needs the line, read in full, not a name or a fragment.
    • Answering a question is not approving a change.
    • A recommendation about an external tool comes from reading all of it, not its README.
    • A new test only counts once it has been seen failing for the expected reason.

    Documents that can’t drift

    Docs-as-code: the documentation lives in the repository and is checked like code.

    • Generated, not written: the infrastructure diagrams on each project page and the database schema snapshot are generated from the code and the live database.
    • Checked: the gate fails if a document is missing from the index or a link to a document is broken. It also fails if an environment variable in code is undocumented, or a user manual quotes text that doesn’t exist in the app.
    • Protected: a hook stops the AI from editing a generated file by hand, and names the command that writes it.
