How I work

I define the problem, the requirements, the data model and the controls. AI coding assistants write and test the code under my direction. Nothing is released until it passes those controls and my review.

Who does what

  • My part: the business problem, the requirements, the data model, the controls, every decision and every approval.
  • The AI’s part: drafting code and tests, running checks and gathering evidence, always against a plan I approved. I use Claude Code.
  • Accountability: I answer for every change, as I would for any process I run.

How a change reaches production

  1. Research first

    Before designing, I look for evidence: dated sources, the current code and the live data. A recommendation about a tool comes from reading the tool, not its description.

  2. A plan with evidence

    The plan states what changes, what stays the same and what happens to existing data. Every claim cites the line of code, the query or the measurement behind it. The plan ends by listing what was verified and what was not.

  3. Challenge the output

    A second pass looks only for assumptions without evidence. For security findings, a separate AI reviewer sees only the finding, not the reasoning behind it, and tries to refute it.

  4. Explicit approval

    Nothing changes without my OK for that specific change. If the plan proves wrong halfway, the work is reverted and planned again, never patched on the fly.

  5. Rehearsal

    The change is built and measured in a disposable copy before it touches the project. A new test counts only after I have seen it fail.

  6. Release under change control

    The same automated checks run before each change is saved, before it is shared and again in continuous integration, and the guardrails block skipping them. Every write to production asks for my confirmation.

What every project guarantees

  • No silent changes: nothing is modified without an explicit approval for that change.
  • No degradation: a change improves or preserves what exists. If it would remove a feature, a validation, a test or a check, it stops.
  • Production under confirmation: database changes, releases and merges ask for confirmation each time.
  • Access by token only: each project uses its own token with the minimum access it needs. Secrets live outside the code, the guardrails block printing them, and interactive logins are blocked.
  • Data minimization: real people’s data is never used as an example or in tests, and the AI reports anonymize it first.
  • Human review (human in the loop): a person keeps the decision. In Corex the coach approves each AI report before it is published; in Fraud Exploration the analyst decides on each alert.
  • Documented decisions: each decision is written down with its reason. Anything the code can generate, such as the infrastructure diagrams, is generated rather than written by hand.
  • Learning from mistakes: every mistake is recorded with its root cause and becomes a rule. A rule that keeps being needed becomes an automated check.
  • The same guardrails everywhere: one shared set of guardrails runs in every project and tests itself at the start of each session. I maintain it as a Claude Code plugin.
