How I work

My strength is business analysis and operations: understanding a process, its risks and its controls. AI is one of my tools for improving them. I run it like any operation with risk: written rules, limited access, review of what it produces, and nothing reaching production without my approval. Below is that environment, piece by piece, and you can try the hooks.

The setup, layer by layer

Each layer covers a different risk: first what the AI can touch, then how it works, and last what happens before production.

  1. Workstation

    settings · fine-grained tokens

    Risk: a session reading another project’s files, or a credential ending up in the code.

    The AI’s file tools can’t read outside the project folders. Credentials live in environment variables, never in the code. GitHub tokens are fine-grained: each one works only for one repository or organization.

  2. Permissions

    allow · ask · deny

    Risk: the AI doing something irreversible on its own, or publishing to production.

    Claude Code’s own permission rules. Some actions are denied outright, such as staging everything at once (git add .) or a force push. Others always ask me first: SQL on the live database, migrations and deploys. So do writes to GitHub through MCP, the protocol that connects the AI to outside services.

  3. Hooks

    plugin · PreToolUse · SessionStart

    Risk: the AI leaking a secret, deleting work or skipping a control, even when it’s allowed to use the terminal.

    Hooks are scripts that Claude Code runs at fixed moments. A plugin I maintain runs one before every action. Its six rules (secrets, destructive commands, git, production, tokens only and its own configuration) read the command, the file or the tool call. Then they deny it, ask me or stay silent. Another hook runs at session start and tests the rules. Changing their configuration needs my yes.

  4. Prompt scaffolding

    CLAUDE.md · rules · lessons

    Risk: the AI working from general habits instead of the project’s rules.

    The instruction files the agent reads before it works. One CLAUDE.md per project says what it is, the protocol, the rules that can’t be broken and which source wins. Path-scoped rules load only when the AI touches that folder, and the lessons from past mistakes load every session.

  5. Skills

    SKILL.md

    Risk: a delicate procedure done differently each time.

    Step-by-step procedures the agent follows: audit, plan, rehearse, review counterparts, commit, handle an incident, resume after a long session. The ones that deploy or migrate end in a command the hook holds until I approve it.

  6. Subagents

    Read · Grep · Glob

    Risk: nobody questioning what the AI proposes before it reaches me.

    Separate agents limited to read-only tools: one checks the plan against my decisions and the code; another tries to refute each security finding.

  7. Git hooks and CI

    pre-commit · pre-push · GitHub Actions

    Risk: broken code getting in, or new code landing on top of something broken.

    The same checks run before every commit, before every push and in continuous integration (CI: the checks GitHub runs on every change). A push is blocked while the main branch’s CI is red, and the checks can’t be skipped.

  8. Production scripts

    Node · Deno

    Risk: publishing to the wrong account, changing data without a rehearsal, or exposing a secret.

    Deploy scripts confirm the target account and project before writing. They can run dry (show what they would do without doing it) and check that what’s served is what was built. Database changes are rehearsed in a transaction that ends in rollback.

    The AI doesn’t handle secret values. The hooks stop it from printing one, and a script checks that a token exists by reporting only its name and length.

The life of a change

  1. Session start
  2. Audit
  3. Plan
  4. Review
  5. Approval human checkpoint
  6. Rehearsal
  7. Commit
  8. Git hooks and CI automatic gate
  9. Release
  10. Resume

  1. Session start

    Before any work, a SessionStart hook hands the session the git state, the latest CI runs and the plugin’s self-test.

  2. Audit

    Every claim is backed by a line of code (file:line), a database query or a measurement. A second pass looks only for assumptions, and what can’t be checked is listed as “not verified”.

  3. Plan with fixed sections

    • Today vs proposed.
    • Why it’s the smallest solution.
    • Impact on what already exists, ending with a mandatory “does not degrade” line.
    • Current code next to proposed code.
    • Verified vs not verified.

  4. Independent review

    A reviewer subagent checks the plan against my decisions and the code. Each finding is fixed or answered before the plan reaches me.

  5. My approval

    An explicit OK for that change. If the plan proves wrong halfway, the work is reverted and planned again, never patched on the fly.

  6. Rehearsal

    The change is built in a disposable copy, and tests, types and the build are measured before and after. Test-first: a new test counts only after it has been seen failing (red before green).

  7. Commit

    Every file and line of the diff is matched against the approved plan, counterparts are reviewed, and files are added by name.

  8. Git hooks, CI and merge

    The pre-commit and pre-push hooks, then a pull request merged only when CI is green on its latest commit.

  9. Release

    By script, with live verification afterwards.

  10. Resume

    If the conversation is compacted, the state is rebuilt from disk (git, the written plan, the live source), never from the conversation’s summary.

Counterparts: if X exists, Y must exist

The code is reviewed as pairs, in both directions where it makes sense: a test whose function no longer exists is also a gap. A pair that fails manual review twice becomes an automated check.

Hooks before every action

Before each action, the plugin’s PreToolUse hook reads the command, the file or the tool call, and decides.

    • No network inside the check: a hook that times out would let the action through, so it never waits on the network.
    • Hard to fool: it reads commands the way the shell does. It catches quoted flags (git push "--force") and variable prefixes (VAR=1 git push -f). It also catches commands nested in another shell (bash -c "…", cmd /c rd /s /q C:\) and scripts passed through a heredoc.
    • Tested: 52 automated tests, and each rule was written after seeing its tests fail. A new version installs only after GitHub confirms its tag is on the main branch and its CI passed.

    A real change: the till that would have stopped saving sales

    A full audit of a sales system’s code found a hidden failure. From sale number 100,000, every new sale would be thrown away while the screen said “saved”. With a setting the owner could change, the limit dropped to 10,000. It hadn’t happened yet.

    1. Root cause, verified in the code

      Two defects in a chain:

      • the receipt number was cut when it outgrew its width, so sale 100,000 reused an existing number;
      • the till read any “duplicate” error as “this sale is already saved” and dropped the sale.

    2. The audit went past the case

      The same pass found two more failures:

      • nothing in the database stopped a receipt from being deleted, except a filter in a test script;
      • the scheduled cleanup failed entirely if a deleted product was still named in a discount.

    3. Plan before touching anything

      Each finding was written down with its verified cause and its proposed fix, not yet applied.

    4. The fix

      • The number grows instead of being cut.
      • The till treats as “already saved” only a repeat of the same sale.
      • The database refuses to delete receipts, except in test businesses.
      • The cleanup keeps the products a discount still names.
      • Each case has its own database test.

    5. Release by script

      The change was generated from the live definitions in the database. The script refused to produce anything if the live code wasn’t exactly what the plan expected.

    6. Verified live

      It was applied to both installations, and the next scheduled cleanup finished successfully in both, according to the database’s own job log.

    Mistakes become controls

    A post-incident loop: every mistake the AI makes ends up as a written lesson. One that repeats ends up as a hook or a CI check.

    1. The AI makes a mistake

    2. It’s recorded

      In the project’s error log: what happened, the root cause, the rule that would have prevented it, and what it cost.

    3. It becomes a lesson

      One line that cites its origin and loads at the start of every session.

    4. If it happens again

      The lesson becomes an automated check (a hook or a CI check) and leaves the written rules.

    Documents that can’t drift

    Docs-as-code: the documentation lives in the repository and is checked like code.

    • Generated, not written: the infrastructure diagrams on each project page and the database schema snapshot are generated from the code and the live database.
    • Checked: the gate fails if a document is missing from the index or a link to a document is broken. It also fails if an environment variable in code is undocumented, or a user manual quotes text that doesn’t exist in the app.
    • Protected: a hook stops the AI from editing a generated file by hand, and names the command that writes it.
